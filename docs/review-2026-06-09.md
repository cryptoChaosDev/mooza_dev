После реализации запущен воркфлоу состязательного ревью (5 ревьюеров по измерениям → проверка каждой находки отдельным агентом, 13 агентов суммарно). Подтверждено **8 реальных проблем**, все исправлены (`b5a558c`):

- **HIGH ×3 — регрессии от unique-индекса ника:** пути `VK /vk/callback`, Telegram `/telegram`, admin создание/правка юзера ставили ник напрямую → при дубле краш регистрации / сырая ошибка БД. Закрыты через `safeNickname` / проверку с чистым 409.

- **LOW:** неиспользуемый проп `country` в `CityPicker` (намеренно, каталог только РФ).

> Вывод: ревью-воркфлоу окупился — поймал 3 HIGH-регрессии, не обнаружимые tsc и не покрытые при ручной реализации.

## 5. Инфраструктурные засады DEV (важно)

DEV развёрнут восстановлением дампа PROD + `prisma db push` (миграции дрейфят). Это породило три «тихие» поломки — фича работает в коде, но молча мертва из-за данных/схемы:

1. **norm-колонки поиска (`*Norm`) были пустыми.** Это Postgres **GENERATED**-колонки, заданные сырым SQL в миграции; `db push` пересоздал их как простые пустые → поиск по имени/нику/каталогу молча не находил никого. Симптом тестировщика: «странный баг» с путаницей пользователей. **Фикс:** пересозданы как GENERATED (98/98 заполнились).
2. **`db push` теперь падает целиком** на generated-колонках (`column ... is a generated column`). Поэтому новые таблицы на DEV создаются **напрямую SQL** — так создана `City`.
3. **Seed-данные из миграций на DEV отсутствуют.** Каталог ролей `Role` сидируется INSERT'ами внутри миграции `20260602010000_seed_roles`; `db push` их не выполняет → таблица пуста → «нельзя назначить роль участнику». **Фикс:** применён SQL миграции (214 ролей).

Все три — артефакты настройки DEV, **на PROD не воспроизводятся** (эти фичи в `master` ещё не вмержены). Зафиксировано в рабочей памяти, чтобы не повторять.
