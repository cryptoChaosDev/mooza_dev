# Runbook: своп серверов PROD ↔ DEV

**Цель:** сделать боевым (`moooza.ru`) сервер **B = 188.120.243.36** (провайдер fvds.ru — надёжнее по РФ), а сервер **A = 81.31.246.105** перевести в DEV (`dev.moooza.ru`). Полный своп с переносом данных. Причина — РФ-доступность/TLS текущего PROD. Окно даунтайма ~15–40 мин.

## Проверенное состояние
| | A = 81.31.246.105 (сейчас PROD) | B = 188.120.243.36 (сейчас DEV) |
|---|---|---|
| Стек | docker compose: postgres16 + api(127.0.0.1:4000) + web(127.0.0.1:3000) за **host-nginx** | тот же |
| Ветка | `master` (HEAD d29764d) | `dev` (HEAD 28dddab) |
| БД (логич.) | **21 МБ**, 117 юзеров | ~тест |
| uploads | **965 МБ** (`server/uploads`, bind-mount) | 880 МБ |
| Данные | боевые (postgres volume `mooza_postgres_data`) | тестовые |
| nginx/SSL | `/etc/nginx/sites-enabled/moooza.ru` + LE `moooza.ru` | LE `dev.moooza.ru` |
| `.env` | секреты PROD (moooza.ru, VAPID/SMTP/TG-токены) | секреты DEV |
| Доступ | напрямую (plink) | с A по SSH-ключу; порты 22/80/443 открыты |

**Что переносим:** логический дамп БД (`pg_dump mooza_db`) + `server/uploads` (rsync) + `.env` (меняем местами) + LE-сертификат (файлы портативны). Данные малы → перенос быстрый; окно тратится на freeze→dump→restore→rebuild→verify→DNS→propagation.

---

## ⛔ Жёсткая зависимость: DNS
A-записи меняете **вы** (у меня нет доступа к DNS-панели):
- `moooza.ru` (+`www`) A → **188.120.243.36 (B)**
- `dev.moooza.ru` A → **81.31.246.105 (A)**

**Заранее** (за сутки, идеально) снизить **TTL** этих записей до 60–300 c, чтобы cutover прошёл быстро. SSL решаем копированием LE-сертификата (см. Фаза 2, п.5) — TLS на новом PROD заработает сразу после переключения DNS.

---

## Фаза 0 — подготовка B (без даунтайма, заранее)
1. На B: `git fetch && git checkout master && git pull` (но НЕ подменяем данные/секреты пока).
2. Дамп **текущей DEV-БД и uploads с B** в архив (чтобы не потерять dev-данные — переедут на A как DEV, либо в отвал по вашему решению).
3. Проверить: docker/дисковое место на B (45 ГБ свободно — ок), certbot установлен.

## Фаза 1 — заморозка PROD (A) [начало окна]
4. **Бэкап PROD (для отката):** `pg_dump -U mooza mooza_db > prod_YYYYMMDD.sql` + `tar czf prod_uploads.tgz server/uploads`. Сохранить копию вне A.
5. Остановить приём записи: `docker compose stop api web` на A (postgres оставить). Показать пользователям заглушку опц.
6. Снять **финальный консистентный дамп** БД A + зафиксировать `server/uploads`.

## Фаза 2 — развернуть новый PROD на B
7. Перенести с A→B: `prod_final.sql`, `server/uploads/`, `A:.env` (это PROD-секреты). `.env` A → B (перезаписать), `.env` B (dev) сохранить для A.
8. На B: `docker compose stop api web`; **restore БД**: `dropdb mooza_db && createdb && psql < prod_final.sql` (внутри mooza-postgres); заменить `server/uploads` боевыми; убедиться `.env` = PROD.
9. **Скопировать LE-сертификат A→B:** `/etc/letsencrypt/{live,archive,renewal}/moooza.ru*` → B (файлы портативны) + конфиг host-nginx `moooza.ru` (server_name+пути) → B, `nginx -t`.
10. На B: `docker compose build web api && up -d` (web пересоберётся с PROD `VITE_API_URL`); `prisma migrate deploy` (на данных master → no-op); локальная проверка: `curl 127.0.0.1:4000/api/health`, `curl 127.0.0.1:3000`.

## Фаза 3 — переключение DNS [вы]
11. Переключить A-записи (см. блок DNS выше). Дождаться пропагации (низкий TTL).
12. Проверить снаружи: `moooza.ru` резолвится в **B**, отдаёт приложение с **боевыми** данными, TLS валиден (по скопированному серту), пуши/логин/лента живые.

## Фаза 4 — превратить A в DEV
13. На A: `git checkout dev && pull`; подменить `.env` на DEV (сохранённый с B); данные — по решению: (а) restore dev-дампа с B, либо (б) оставить копию боевых как DEV (учтите PII на DEV).
14. host-nginx A → `dev.moooza.ru` (+ LE `dev.moooza.ru`: скопировать с B или перевыпустить certbot'ом когда `dev.moooza.ru` → A).
15. `docker compose build && up -d`; `migrate deploy` (применит 6 ожидающих миграций на dev-БД).
16. Проверить `dev.moooza.ru` → A отдаёт dev.

## Фаза 5 — финализация
17. Настроить **автопродление LE** (certbot renew) на обоих (домены теперь на других серверах).
18. Обновить деплой-скрипты/jump-хост (теперь PROD=B, DEV=A) и память проекта (`project_deploy`).
19. **Проверить РФ-доступность нового PROD** (главная цель) — check-host/зонд с релея.

## Откат
A остаётся **нетронутым** и с бэкапом до подтверждения B. Сбой → вернуть DNS `moooza.ru` → A, поднять `api/web` на A. Потеря данных = только записи за окно заморозки (их не было, api был остановлен).

## Решения (подтверждены)
- ✅ DNS-доступ у заказчика есть — он снижает TTL заранее и переключает A-записи в Фазе 3.
- ✅ Порядок: **сначала снизить TTL** → дождаться пропагации → потом окно cutover.
- ✅ DEV-данные на A: **перенести текущий dev-дамп+uploads с B** (Фаза 0 п.2 → restore на A в Фазе 4, вариант «а»). Без PII на DEV.

## Сейчас (действие заказчика, перед окном)
Снизить **TTL** до 300 c (или 60) на A-записях `moooza.ru`, `www.moooza.ru`, `dev.moooza.ru`. Затем **подождать ≥ старого TTL** (напр. час), чтобы низкий TTL разошёлся по кэшам — тогда сам cutover переключится за ~5 мин. Как будете готовы к окну — дайте сигнал, начинаю Фазы 0–2.
